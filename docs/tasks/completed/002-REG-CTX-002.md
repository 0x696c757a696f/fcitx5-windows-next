# Current Task — REG-CTX-002 CandidateModel A→B→A Ordering

**Mode:** CHANGE  
**Priority:** next unfinished stabilization task after `REG-UILESS-001`  
**Task ID:** `REG-CTX-002`

## Goal

Fix CandidateModel stale-snapshot detection so ordering is scoped to the correct context/composition identity.

A legitimate snapshot for context A must not be rejected merely because a different context B previously used a numerically larger `composition_id`.

Required regression:

```text
A(ctx1, comp1, rev10)
→ B(ctx2, comp2, rev1)
→ A(ctx1, comp1, rev11)
```

The final A snapshot is newer for A and **must be accepted**, even if `comp1 < comp2`.

## Known audit observation — verify against current HEAD

The reproducible audit baseline observed stale filtering equivalent in effect to:

```text
if same context and incoming revision < current revision:
    stale

if incoming composition_id < current composition_id:
    stale
```

The second comparison was not sufficiently scoped to the same context/composition lineage, so activity in context B could make a later valid snapshot for context A look stale.

This is evidence to investigate, not permission to assume current HEAD is unchanged. Trace current CandidateModel code and tests before editing.

## Required identity model

Freshness must be reasoned about using the scoped identity:

```text
(engine_epoch, context_id, composition_id, revision)
```

These fields do **not** form one globally increasing integer tuple.

Required semantics:

1. `engine_epoch`
   - separates engine lifetimes;
   - an older epoch must not overwrite the current epoch.

2. `context_id`
   - separates independent input contexts;
   - composition IDs from different contexts must never be ordered against each other as one global counter.

3. `composition_id`
   - identifies a composition lineage inside its valid context/epoch scope;
   - compare it only where the current protocol/runtime contract guarantees meaningful ordering.

4. `revision`
   - orders updates inside the same authoritative context/composition lineage;
   - an older revision must not overwrite a newer revision for that lineage.

Do not invent a global total ordering if the protocol only guarantees scoped ordering.

## Required behavior

### Case A — same context/composition, older revision

```text
A(ctx1, comp1, rev10)
A(ctx1, comp1, rev9)
```

`rev9` is stale and must be rejected.

### Case B — different context

```text
A(ctx1, comp1, rev10)
B(ctx2, comp2, rev1)
```

B must not be rejected merely because its counters are numerically lower than A's.

### Case C — A→B→A regression

```text
A(ctx1, comp1, rev10)
B(ctx2, comp2, rev1)
A(ctx1, comp1, rev11)
```

Final A `rev11` must be accepted.

### Case D — stale A returns after newer A

```text
A(ctx1, comp1, rev10)
B(ctx2, comp2, rev1)
A(ctx1, comp1, rev12)
A(ctx1, comp1, rev11)
```

Final `rev11` must be rejected for A.

### Case E — epoch rollover

A snapshot from an older `engine_epoch` must not overwrite state belonging to the current epoch.

### Case F — composition transition

When A starts a new composition, stale updates from A's previous composition must not overwrite the new one. Use the actual current protocol guarantees; do not assume composition IDs are globally monotonic across unrelated contexts.
